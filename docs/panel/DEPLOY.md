# Deploying Main

Main is one container plus a database and a reverse proxy. Everything it knows
lives in MariaDB, so a deployment is: put the compose stack up, point two DNS
names at it, and add nodes from the panel.

Nodes are *not* deployed from here. A node gets one command, generated by the
panel, and that command pulls the agent and the cores from the panel itself -
see [Adding a node](#adding-a-node).

## What you need

* A host with Docker and the Compose plugin. 1 GB of RAM is enough for the
  panel; the image is built elsewhere or here, and building needs ~2 GB, so on
  a small host either add swap or build the image on your own machine.
* Two DNS names already pointing at the host:
  * one for the panel, e.g. `panel.example.com`;
  * one for subscription links, e.g. `sub.example.com`.
  Two names rather than one because a subscription host is the part that gets
  handed out and therefore the part that gets blocked, and losing it should not
  cost you the panel. [One name](#one-name-instead-of-two) is possible.
* Ports 80 and 443 free (Caddy, TLS and the ACME challenge) and one port for
  the agents, 8443 by default.

## Install

```bash
git clone https://github.com/thehavlok/whitenet.git
cd whitenet/deploy
cp .env.example .env
```

Generate the master key and put it in `.env`:

```bash
docker compose run --rm --no-deps --entrypoint wn-main main genkey
```

The master key encrypts every secret in the database: Reality private keys,
Shadowsocks passwords, OpenFlux channel secrets, the node CA key. **Back it
up.** Losing it means losing all of them; changing it makes them unreadable.
Nothing else in `.env` is hard to replace.

Fill in the rest of `.env` - the database password, the two domains, and
`WN_GRPC_ADVERTISE` - then:

```bash
docker compose up -d
docker compose logs -f main
```

The panel migrates its own schema on start, so there is no separate migration
step. The log ends with the listening addresses once it is up.

Open `https://panel.example.com/admin/` and create the first administrator.
That form works exactly once: as soon as one administrator exists the endpoint
refuses, so an unattended panel cannot be claimed by whoever finds it first.
Turn on two-factor straight away in **Account** - the panel is the one host
that can reach every node.

Then, in **Settings**:

* **Panel URL** and **Subscription URL** - these go into install commands and
  into the links users are given, and nothing derives them for you because
  only you know which name is meant to be public.
* **Agent endpoint** - `panel.example.com:8443`, what agents connect to.
* Branding and the defaults for new users.

## Adding a node

**Nodes → Add node** asks for a name and a group and gives you one line:

```bash
curl -fsSL https://panel.example.com/install.sh | bash -s -- \
  --token <TOKEN> --main panel.example.com:8443 --ca-fingerprint <SHA256>
```

Run it on the node as root. It installs the agent and xray-core, writes a
systemd unit, enrols with the token and starts. The token is single-use and
expires; the fingerprint is what stops a node from being talked to by anything
but your panel.

The node needs no inbound ports open for this - the agent dials out - only the
ports its own inbounds listen on.

## Upgrading

```bash
git pull
docker compose build
docker compose up -d
```

The schema migrates on start. Agents are upgraded separately, from
**Nodes → Update**, which is deliberate: the panel and its nodes are allowed
to be a version apart, and a node that is offline during an upgrade converges
when it comes back.

## Backups

Two things, and only two:

```bash
# 1. the database
docker compose exec -T db mariadb-dump -u root -p"$(docker compose exec -T db \
  sh -c 'echo $MARIADB_ROOT_PASSWORD')" --single-transaction whitenet > whitenet.sql
# 2. the master key
grep WN_MASTER_KEY .env
```

A dump without the key is unreadable where it matters, and the key without a
dump is nothing. Keep them together, and keep them somewhere other than this
host.

Caddy's `/data` volume holds the certificates. It is worth keeping to avoid
re-issuing, but it is not a backup requirement.

## One name instead of two

To serve the panel and the subscriptions on a single name: delete the second
site block from `Caddyfile`, and set `WN_SUB_DOMAIN=` (empty) in `.env`. The
panel then answers subscriptions on whatever host it is asked about. You lose
the separation described above - a blocked subscription host takes the panel
with it.

## Running without Docker

The binary is self-contained: the admin interface is embedded in it and the
only dependency is MariaDB.

```bash
cd web && npm ci && npm run build && cd ..   # interface → internal/panel/webui/dist
go build -o /usr/local/bin/wn-main ./cmd/wn-main
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -o /opt/whitenet/dist/wn-agent-linux-amd64 ./cmd/wn-agent
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -o /opt/whitenet/dist/whitenet-linux-amd64 ./cmd/whitenet
cp main.example.toml /etc/whitenet/main.toml   # then fill it in
wn-main -config /etc/whitenet/main.toml serve
```

`/opt/whitenet/dist` is where the installer looks for the builds it hands to a
node; `WN_DIST_DIR` moves it. Put a reverse proxy with TLS in front of
`http.listen`, and leave `grpc.listen` reachable directly - it is mutual TLS
and must not pass through an HTTP proxy.

## What listens where

| Port | Who | Why |
| --- | --- | --- |
| 443, 80 | Caddy | TLS for the panel and the subscriptions; 80 redirects and answers ACME |
| 8080 | the panel | HTTP behind Caddy, never published |
| 8443 | the panel | agents, mutual TLS, published directly |
| 3306 | MariaDB | inside the compose network only |

`WN_TRUSTED_PROXIES` decides whose `X-Forwarded-For` the panel believes, and
the subscription rate limit and the device ledger both depend on a truthful
client address. Compose sets it to the private ranges because Caddy's address
in a Docker network is assigned at run time; port 8080 is not published, so
nothing else can reach it to lie.
